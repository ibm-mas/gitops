F-12 + F-03 (combined) — Encrypt failure leaves a silent manifest gap

HIGH F-12 / F-03 backup-suite-manage.sh:111–112  |  dr_lib.py:619–624  |  dr_lib.py:593–643 (validate_manifest)

Failure mode (exact trace):

When python3 "$LIB" store exits non-zero (line 111) — due to an encrypt failure, a Python exception, or a SystemExit — the shell at line 112 only increments FAILED and prints an ERROR to stderr. It does not call record-skip. The object therefore appears in neither .records.jsonl nor .skips.jsonl.

At manifest time, validate_manifest (line 593) checks required resources through the skips array at line 622–624:

for s in manifest["skipped"]:
    if s["required"] and s["status"] != "skipped_policy":
        errors.append(f"required resource {s['id']} not backed up: {s['reason']}")

Because the failed object is not in .skips.jsonl, this loop cannot fire for it. The inventory completeness check at line 632–635 can catch it only when --discover was used; without discovery, no completeness check runs.

Concrete scenario: an encrypt command fails on main-manage-encryption-secret (required). FAILED becomes 1 → the backup exits 2. But manifest["validation"]["ok"] is true, and the manifest's skipped list contains no trace of the failure. Any downstream consumer that only checks the JSON manifest (e.g. an automation that reads "ok": true) would see a clean manifest for an incomplete backup.

The two findings share one root cause: the shell error handler at line 112 does not call record-skip. Fixing that one line resolves both F-03 (audit trail) and F-12 (manifest accuracy).

Precise fix location:

# backup-suite-manage.sh line 111-112 (current)
    printf '%s' "$json" | python3 "$LIB" store --out "$OUT" --required "$required" --source "$source" ||
      { FAILED=$((FAILED + 1)); echo "ERROR: could not store $kind/$name" >&2; }

# proposed change: record the failure in .skips.jsonl so manifest can see it
    printf '%s' "$json" | python3 "$LIB" store --out "$OUT" --required "$required" --source "$source" || {
      FAILED=$((FAILED + 1))
      echo "ERROR: could not store $kind/$name" >&2
      python3 "$LIB" record-skip --out "$OUT" --kind "$kind" --name "$name" --namespace "$ns" \
        --required "$required" --status "failed" \
        --reason "store command failed (encrypt error or Python exception)" --source "$source"
    }

After this fix, validate_manifest's existing check at line 622–624 will catch the required-resource failure in the manifest, producing "ok": false.

New test required: run a backup with an encrypt command that succeeds on the first few objects and fails on a required one; assert proc.returncode == 2, manifest["validation"]["ok"] == False, and the required resource appears in manifest["skipped"].

F-08 — manual_blockers not enforced by apply --execute

MEDIUM F-08 restore.py:128–143 (_blockers)  |  restore.py:259–295 (apply_plan)

_blockers at line 128 assembles a list that is displayed in the plan but never checked by apply_plan. There are four kinds of blocker; they are not equally important:

Blocker textRisk if --execute proceedsRecommended gate?
"backup is plaintext; do not move it off the source workstation"High: plaintext Secrets are being piped to a target cluster over a network connection or from a shared pathYes — block --execute
"CA key pairs were NOT exported (policy)"Medium: cert-manager will mint a new CA; this is an architectural decision, not a data-loss risk during the apply itselfWarn, do not block
"CA key pairs are in the backup but not selected"Low: user simply needs --include-optin; caught before this pointNo change needed
"operator adoption of restored Secrets and Manage data decryption are unproven"Low: always present; blocking --execute forever is not usefulNo — keep as advisory

Only one blocker needs to become a hard gate: the plaintext blocker. The current code at line 130 is:

if not manifest["encryption"]["secrets_and_files_encrypted"]:
    b.append("backup is plaintext; do not move it off the source workstation")

This produces a visible warning in the printed plan. But apply_plan at line 259 only gates on preflight errors and plan["problems"]. A plaintext backup can reach --execute without any additional obstacle.

Precise fix: in apply_plan, check manifest["encryption"]["secrets_and_files_encrypted"] when execute=True and raise RestoreError before any oc create is attempted:

# restore.py — add inside apply_plan, after the plan["problems"] check (line 267):
if execute and not manifest["encryption"]["secrets_and_files_encrypted"]:
    raise RestoreError(
        "--execute refused: backup is plaintext. Re-run backup with DR_ENCRYPT_CMD set "
        "before applying to a target cluster."
    )

Conflict to note: this would make the existing test test_apply_execute_uses_create_and_never_overwrites (line 663) fail, because it uses a plaintext backup with execute=True. That test would need to use an encrypted backup fixture for the execute=True path, OR the test and the production flow need separate treatment (dry-run is unaffected; the gate only applies when execute=True).

New test required: assert that apply_plan(..., execute=True) raises RestoreError matching "plaintext" when the manifest has secrets_and_files_encrypted: false. Separately, a dry-run with a plaintext backup must still succeed.

F-11 — skipped_exists silently passes for required Secrets

MEDIUM F-11 restore.py:287–289 (apply_plan)  |  restore.py:294–295 (apply_plan return)

The return value at line 294–295:

return {"executed": execute, "overwrite": overwrite, "results": results,
        "ok": all(r["result"] in ("created", "dry-run-ok", "skipped_exists") for r in results)}

counts skipped_exists as a success. The problem is not that skipping an already-present object is wrong — it is a legitimate choice when --overwrite is not given. The problem is that the ok field does not distinguish between "everything was created fresh" and "some required objects were silently skipped because they already existed."

Scenario: a previous failed restore left a stale main-manage-encryption-secret on the target with the wrong key material. A new restore run sees AlreadyExists, records skipped_exists, and returns "ok": true. The operator reads "apply: OK" in the terminal and believes the restore succeeded. The Manage data may be unreadable.

There is no conflict with the existing test (line 663–672). That test asserts skipped_exists for a required Secret and does not assert rep["ok"] as True for a complete restore — it only checks that the per-item result is skipped_exists. The fix must not break that.

Recommended fix — two-part:

  1. Add an ok_no_skips boolean to the report: all(r["result"] in ("created", "dry-run-ok") for r in results). This is a new field and is backward compatible.
  2. When any step with skipped_exists is for a required entry (cross-reference with manifest["entries"]), add a warning to the report. The plan already carries entry["required"], so the check is a single loop.

Alternatively, consider making skipped_exists on a required resource a non-ok result. That would force the operator to either use --overwrite or manually verify the existing resource before running again. This is a stricter but safer posture.

New test required: assert that when execute=True and a required entry (e.g. main-manage-encryption-secret) is already present, the report either has ok_no_skips=False, or that the final summary message clearly surfaces the skip.

F-09 — Cross-stage dependency ordering: advisory vs. blocking

MEDIUM F-09 restore.py:166–175 (build_plan)  |  restore.py:263–267 (apply_plan)  |  tests/test_dr.py:495–510

Re-read clarification: the original review was correct in identifying the mechanics, but the severity needs a precision adjustment. The problems list IS checked by apply_plan at line 266–267:

if plan["problems"]:
    raise RestoreError("plan has ordering problems:\n  " + "\n  ".join(plan["problems"]))

So problems already blocks apply. The actual gap is in the sequence of operations:

  1. order_entries(items) runs Kahn topological sort (correct order, dependencies first).
  2. ordered.sort(key=lambda i: i["stage"]) then re-sorts by stage — stable, so topological order within a stage is preserved, but cross-stage order can be violated.
  3. The problems detection loop at line 171–175 runs after the re-sort and correctly identifies cross-stage violations. Those violations then block apply.

The actual defect: the stage-sort at step 2 can create violations that are correctly detected at step 3, causing the plan to be unusable for any manifest where a restorable object at a lower stage has a dependency on a restorable object at a higher stage. Neither of those cases exists in today's test data (all restorable items are Secrets/ConfigMaps → stage 5; their dependencies are also Secrets/ConfigMaps → stage 5). The defect is latent, not currently triggerable.

Why it matters: if a future resource type (e.g. a custom CR restored to stage 7) depends on a restorable Secret (stage 5), the stage-sort would put the Secret before the CR (correct), but if the order were reversed (CR at stage 3, Secret at stage 5), the plan would emit a problem and refuse to run — which is the safe outcome. The real danger is the opposite direction: a Secret that depends on a higher-stage CR would never be caught until a real test exposes it, because today's test only confirms plan["problems"] == [].

Current status of the blocking gate: the gate is present and works. The issue is that the stage-sort can render a semantically valid dependency graph unexecutable. The fix is to remove the post-topological stage-sort and instead assign stage as a tiebreak key inside the topological ordering, or to validate before sorting that no stage-boundary violations exist in the dependency graph.

Recommended minimal fix: replace the post-topological sorted() call with a sort that uses max(stage, stage_of_all_ancestors) as the effective stage for each item, preserving dependencies. Alternatively, simply document the constraint that no restorable item may have a higher-stage dependency and add a test that constructs such a plan and verifies problems != [].

New test required: construct a plan where a stage-5 item depends on a stage-7 item; assert plan["problems"] != [] and that apply_plan raises RestoreError.

F-04 — Encrypted payload not verified as decryptable

MEDIUM F-04 dr_lib.py:598–612 (validate_manifest)  |  dr_lib.py:640–642

Re-read confirms the design constraint: the tool explicitly skips content-validation for encrypted files and emits a warning (line 641: "N encrypted files not content-validated (decrypt needed)"). The README acknowledges this under "Encryption and sensitive data". The fix here is purely documentation, not code.

What the code does correctly: checksum covers ciphertext (bit-rot detected); file permission checked (mode 600 enforced); MANIFEST entry records encrypted: true. The warning is always present so an operator running verify will see it.

Gap remaining: there is no offline-decryptable smoke test. If DR_DECRYPT_CMD is available at verify time, the tool could optionally decrypt-and-validate. Without a team-approved encryption mechanism this is a design decision, not a bug.

Documentation addition needed: add one sentence to README.md under "Encryption and sensitive data" clarifying that dr_lib.py verify cannot prove decryptability — the operator must manually decrypt one file after backup to confirm the key/command work before the backup is relied upon for recovery.

No code change needed.

F-05 — SHA256SUMS: integrity vs. corruption only (threat-model gap)

MEDIUM F-05 dr_lib.py:583–589 (build_manifest)  |  dr_lib.py:667–683 (verify_sha256sums)

Re-read confirms the scope: SHA256SUMS is computed over all stored files plus MANIFEST.json. An attacker with write access to the backup directory can replace any file and recompute SHA256SUMS in one pass — there is no HMAC or signature. This is consistent with the design (no approved encryption/signing standard exists), but the threat model is not documented.

What the code does correctly: accidental bit-rot, partial writes, and tampering by anyone without access to the backup directory (e.g. git commit, network transfer) are all detected.

Threat model that SHA256SUMS does NOT cover: an adversary (or a bug in the backup script itself) with write access to the same filesystem path after backup completes.

Mitigation already in place: mode 700 on the directory and mode 600 on all files limit write access to the owning user, so the threat requires privilege escalation — not just directory access.

Recommended action: add one sentence to the README noting this boundary: "SHA256SUMS detects accidental corruption and any modification by a process that does not hold write access to the backup directory. It does not protect against an attacker or process running as the same user who performed the backup."

No code change needed.

F-01 — Test gap: --store-reference-secrets + sentinel check

LOW F-01 tests/test_dr.py:362–369 (test_secret_values_never_in_stdout_stderr_or_reports)  |  dr_lib.py:466–474 (cmd_store policy skip)

The existing sentinel test at line 362 runs the backup with --discover but without --store-reference-secrets. With that flag absent, reference Secrets are skipped by policy and never reach yaml.safe_dump. The concern is whether a reference Secret's data could appear in a stored YAML file when --store-reference-secrets is given.

Looking at the code path: cmd_store at line 478 calls sanitize(obj, MODE_REFERENCE) for reference objects. sanitize does not pop the data field — Secret data is preserved in the reference copy. So when --store-reference-secrets is used, the stored YAML file for a reference Secret does contain data: with base64-encoded values. This is intentional (it is a "break-glass copy"), but the sentinel test does not cover this path.

Required test:

def test_break_glass_sentinel_not_in_stored_yaml_files(self):
    proc, out = self.run_backup("--allow-plaintext-local", "--store-reference-secrets")
    for root, _, files in os.walk(out):
        for f in files:
            if f.endswith(".yaml"):
                with open(os.path.join(root, f)) as fh:
                    content = fh.read()
                # SENTINEL_B64 (the base64-encoded sentinel) WILL appear in data: fields;
                # the plain SENTINEL string must not appear anywhere outside data fields.
                self.assertNotIn(fakes.SENTINEL, content.replace(fakes.SENTINEL_B64, ""))

Note: the test correctly uses .replace(SENTINEL_B64, "") to ignore the data field itself — the invariant is that the raw string never leaks outside a properly encoded data field (e.g. not in a label, annotation, or last-applied-configuration). The existing test at line 372–378 already does this correctly for its scope; the new test extends it to the --store-reference-secrets path.

F-13 — Test gaps: partial encrypt failure and thread-safety

LOW F-13 tests/test_dr.py:246–273 (BackupEndToEndTests)  |  tests/test_dr.py:490–492

Gap 1: partial encrypt failure. The existing test at line 490 uses an encrypt command that always fails. It does not exercise the case where encryption succeeds for some objects and fails on a specific required one — which is the scenario that F-12 is about. After F-12's fix, a test is needed that:

  • Provides an encrypt command that fails only on the first Secret (by counting calls, or by detecting the resource name in the input via a helper script).
  • Asserts exit 2, and that the required resource appears in manifest["skipped"] with a recognisable reason.
  • Asserts manifest["validation"]["ok"] == False.

A simpler proxy: use an encrypt command that always succeeds, but patch cmd_store to raise on a named resource. Since the test setup is end-to-end (shell → subprocess), the practical approach is a helper script that exits 0 for the first N calls and exits 3 for call N+1, using a counter file in $TMPDIR. That is somewhat complex; a simpler approach is to test the failure recording path at the unit level by calling record-skip directly and then checking build_manifest.

Gap 2: thread safety of _cache. The class-level _cache = {} at line 246 and the fixture counter at line 240 (len(os.listdir(self.tmp))) are race-prone under parallel execution. unittest is single-threaded by default, so this is not a live bug. No code change needed; a comment noting the limitation is sufficient.

Gap 3: no test for the ordering-violation blocking gate (F-09 test). After F-09 is addressed, add a test that builds a plan with a known cross-stage dependency and asserts it is either reordered correctly or surfaced as a problem that blocks apply.

F-14 — saas-envs: real Let's Encrypt private keys committed to git (URGENT)

EXTERNAL / URGENT F-14 saas-envs/gitops/aws-dev/us-east-2/fvtsaas/fvtsaas*/manual-certs/*/tls.key

What was found (without reading key material):

  • 20 tls.key files exist across two fvtsaas instance directories.
  • The header of one file (one line only) reads -----BEGIN RSA PRIVATE KEY-----, confirming PEM-encoded RSA private key material.
  • The co-located tls.crt has subject CN=admin.fvtsaas.ibmmasfvt.com, issuer Let's Encrypt YR1, validity window 2026-08-24 to 2026-11-22. These are real, Let's Encrypt-signed certificates for a live IBM FVT SaaS domain — not self-signed test material.
  • The files are tracked in git with 766 commits of history. There is no .gitignore suppressing them, no .pre-commit-config.yaml, and no detect-secrets baseline in this repository.
  • File permissions on disk are -rw-r--r-- (world-readable), consistent with a normal git checkout.

Risk assessment: any user with read access to the saas-envs repository (and its git history) can extract these private keys. The corresponding certificates are valid until November 2026. An attacker with the private key can impersonate admin.fvtsaas.ibmmasfvt.com and any other hostnames in the certificate's SANs until expiry or revocation.

This is outside the scope of the DR POC code, but it is directly relevant to the DR project: if the goal is to protect sensitive key material in backups, the team is already committing equivalent material to a repository without encryption.

Recommended immediate actions (by the saas-envs owners, not by this POC):

  1. Revoke the Let's Encrypt certificates immediately using the ACME revoke endpoint.
  2. Rotate the private keys and reissue the certificates.
  3. Remove the key files from git history using git filter-repo or BFG Repo Cleaner.
  4. Add a .gitignore entry for *.key under manual-certs/.
  5. Add a detect-secrets pre-commit baseline that would have caught this.

This audit does not open, print, or expose the key bodies. The above assessment is based on file headers, certificate metadata, and git log only.
