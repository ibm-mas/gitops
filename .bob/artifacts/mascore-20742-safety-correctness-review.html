Area 1 — Discovery: Secret values never printed

LOW F-01 discover.py:52-56  |  dr_lib.py:477  |  tests/test_dr.py:362-369

Finding (no action required before live discovery): Secret data/stringData is popped in discover.py at lines 53–55 before any classification or serialisation. The dr_lib.py store command records only data_keys (line 477). The sentinel test at test_dr.py:362-369 asserts the raw SENTINEL value and its base64 form never appear in stdout, stderr, MANIFEST.json, inventory.json, inventory.txt, README.txt or SHA256SUMS.

Gap (Low): The sentinel test reads every report file with open(..., "rb").read().decode("utf-8", "replace"), so binary-encoded ciphertext is checked. However, the in-memory flow through yaml.safe_dump(clean) in dr_lib.py:478 is not separately validated to confirm the Secret data field survives in cleaned reference copies when --store-reference-secrets is active. Reference copies do not call sanitize in MODE_RESTORE, so data passes through. The test at line 362 uses --discover but does not also use --store-reference-secrets. A targeted test for that combination would close the gap, though the code path is straightforward.

Overall: the primary protection is solid. This is a test-coverage gap only.

Area 2 — Backup encryption: fail-closed; hook validation

HIGH F-02 dr_lib.py:356-364 (encrypt_bytes)  |  dr_lib.py:367-372 (decrypt_bytes)

Decrypt hook does not check for empty output.

def decrypt_bytes(data: bytes, cmd: str) -> bytes:
    proc = subprocess.run(shlex.split(cmd), input=data, capture_output=True)
    if proc.returncode != 0:
        raise RuntimeError(f"decrypt command failed (rc={proc.returncode})")
    return proc.stdout  # ← no emptiness check

encrypt_bytes raises RuntimeError if proc.stdout is empty (line 362–363). decrypt_bytes does not. A decrypt command that exits 0 but writes nothing would cause yaml.safe_load(b"") → None in restore.py:67, which then passes None into api_available(None.get("apiVersion", ""), ...) and raises an AttributeError. That would surface as an unhandled exception — not as a clean RestoreError — during a real restore apply. The test at test_dr.py:490 only covers a non-zero exit code for encrypt, not for decrypt.

Recommended fix: Add the same guard to decrypt_bytes: if not proc.stdout: raise RuntimeError("decrypt command produced no output").

MEDIUM F-03 dr_lib.py:479-484 (cmd_store)  |  backup-suite-manage.sh:99-101

Encryption failure exits the Python store subprocess with status 1, but the shell silently discards FAILED items when they are "optional".

When encrypt_bytes raises (line 484), the cmd_store function propagates as an unhandled exception and the Python process exits non-zero. The shell wrapper at line 100–101:

printf '%s' "$json" | python3 "$LIB" store ... || \
  { FAILED=$((FAILED + 1)); echo "ERROR: could not store $kind/$name" >&2; }

increments FAILED and prints an ERROR. The final gate at line 229:

if [[ $rc -ne 0 || $REQUIRED_MISSING -gt 0 || $FAILED -gt 0 ]]; then
  echo "RESULT: FAILED validation" >&2; exit 2; fi

correctly causes the overall backup to exit 2 when any required object fails, and also when any fetch/store failure (FAILED > 0) occurs. So the fail-closed property holds. The test at test_dr.py:490-492 verifies exit 2 for an encrypt failure.

Gap (Medium): A missed file is recorded in FAILED and the run exits 2, but the object is not added to .skips.jsonl; it simply does not appear in .records.jsonl either. Therefore build_manifest has no trace of the attempted-but-failed store, which means validate_manifest can only flag it if discovery was run (via the inventory["entries"] completeness check). Without discovery, a failed encryption write on an optional resource produces a run that exits 2 but the manifest carries no record of the gap — it could be confused with a transient error after the fact. Adding a record-skip call in the shell error handler would give a complete audit trail.

MEDIUM F-04 dr_lib.py:606-610 (validate_manifest)  |  tests/test_dr.py:477-488

Encrypted files are checksummed as ciphertext, not validated for content or structure.

The validation loop at line 597 correctly skips content checks for encrypted entries (continue after incrementing enc_files at line 609). A warning is emitted (line 640). The SHA256 on disk covers the ciphertext, so bit-rot is detected. However:

  • There is no facility to decrypt-and-validate during dr_lib.py verify even when DR_DECRYPT_CMD is available. A corrupt or incorrectly encrypted file is not detected until a restore attempt.
  • The manifest's data_keys field for an encrypted Secret cannot be cross-checked against the decrypted payload.

This is by design for now (the README acknowledges it), but it means an encrypted backup could hold unreadable files and still pass verify. It is rated Medium because the operator is already warned, and the encrypted test at line 477 confirms the plumbing, not the decryptability.

Area 3 — Checksum coverage and tamper detection

MEDIUM F-05 dr_lib.py:583-587 (build_manifest)  |  dr_lib.py:665-681 (verify_sha256sums)

MANIFEST.json is checksummed in SHA256SUMS but is not covered by the in-manifest checksums, creating a circular trust dependency.

The build sequence is: (1) compute per-file sha256 → embed in MANIFEST.json, (2) write MANIFEST.json, (3) compute sha256 of MANIFEST.json → append to SHA256SUMS. So verify_sha256sums does check MANIFEST.json's hash. However:

  • An attacker who can modify files on the backup host can replace both a YAML file and recalculate SHA256SUMS in one pass, since SHA256SUMS is a flat file with no signing.
  • There is no MAC or digital signature over the whole backup. This is consistent with the design (no encryption standard decided), but the documentation does not warn that SHA256SUMS provides integrity only against accidental corruption, not against an adversary with write access to the backup directory.

The tamper-detection test at test_dr.py:411-417 correctly verifies that file modification is caught. This finding is about the documentation boundary, not a code bug. Rating: Medium (documentation/threat-model gap).

Area 4 — Source-cluster anti-targeting

HIGH F-06 restore.py:212-233 (preflight)  |  tests/test_dr.py:561-584

The source-context check can be bypassed if the backup's source_context is empty.

if ctx.strip() and manifest.get("source_context") and ctx.strip() == manifest["source_context"]:
    errs.append("current context equals the backup's source context; restore there is forbidden")

This check is short-circuited when manifest["source_context"] is falsy (empty string). In backup-suite-manage.sh at line 84:

--source-context "$(oc config current-context 2>/dev/null || true)"

If oc config current-context fails (no kubeconfig context, older oc, minimal env), the value is an empty string, and cmd_init writes "source_context": "" to .dr-config.json. A restore operator who then runs against any cluster would not trigger the context guard — only the server URL guard applies.

The server URL guard is the primary defence and remains active: it checks that the typed --target-server equals the logged-in server AND that the logged-in server is not the backup's source server. If the server URL was also empty (e.g. the backup was taken from a mis-configured kubeconfig), both guards would be weakened simultaneously.

Test coverage at line 561-578 covers both source-URL and source-context refusal; both pass. But neither test exercises the empty-source-context bypass path.

Recommended fix: Emit a warning (or error) from cmd_init and from preflight when source_server or source_context is empty, since that means the safety net is degraded.

MEDIUM F-07 restore.py:218-220 (preflight)  |  restore.py:293 (CLI)

The --target-server typed confirmation uses trailing-slash normalisation but no scheme/hostname normalisation.

if target_server.rstrip("/") != server.rstrip("/"):
    errs.append("--target-server ... does not equal the logged-in server ...")

This correctly requires the operator to type the URL exactly as returned by oc whoami --show-server, which is a good deliberate friction mechanism. The mismatch will catch most accidents. However, semantically equivalent variants (scheme capitalisation, extra path segment, IPv6 vs hostname, DNS alias) would pass the server guard but fail the typed-confirmation guard — meaning the result is a confusing "does not equal" error rather than a safety silence. This is not a bypass; it is a usability friction point with a safety-adjacent consequence.

Tests at line 574-578 confirm the mismatch error. No bypass is possible through this path.

Note: the test at line 561 also confirms that no create/apply call is made when preflight fails — verified by checking run.calls.

Area 5 — Dry-run as default; --execute bypass paths

MEDIUM F-08 restore.py:244-280 (apply_plan)  |  restore.py:296-306 (main)

Dry-run is the default and --execute cannot bypass integrity, preflight, or ordering checks. However, plan["manual_blockers"] is displayed but does not block apply.

The call sequence is: load_backup (integrity check + checksum verification) → build_plan → apply_plan (preflight check → plan-problems check → per-step API check). All of these run before any write, regardless of --execute.

Gap: manual_blockers in the plan (line 125-139) includes items like "CA key pairs not exported", "operator adoption unproven", and "backup is plaintext". These are printed in the plan header but are not checked by apply_plan; they do not block apply --execute. An operator who reads the plan text carefully will see them, but there is no programmatic gate. For example, a plaintext backup can be applied to a target cluster with --execute — the backup directory's permission check is done at backup time, not re-verified at apply time.

Tests at line 586-596 confirm dry-run produces --dry-run=server and dry-run-ok results. Tests at line 609-616 confirm stop-at-first-failure. No bypass of these is possible through the public CLI. The manual_blockers issue is a process gap, not a code bypass.

Area 6 — Operator/GitOps-owned resources not blindly applied

This area is PASS. The classify → backup_mode → restore_eligible chain is clearly enforced:

  • dr_lib.py:527-533: _discover_stores — reference-only Secrets are never stored.
  • dr_lib.py:492-493: restore_eligible is set only when backup_mode == MODE_RESTORE.
  • restore.py:149-150: only restore_eligible entries (or explicit --include-optin) enter the plan as action="apply".
  • restore.py:256-269: only steps with action=="apply" are submitted to oc.
  • CRDs, CSVs, Subscriptions, OLM objects are given MODE_NONE or MODE_REFERENCE by classify; they are in the plan as manual/gitops steps but never sent to oc create.
  • Tests at test_dr.py:495-510 confirm Suite and ManageWorkspace are excluded from the apply set.

Caveat: The Suite and ManageWorkspace CRs are stored as reference copies (not restored), but their spec — including GitOps-reconciled state — does reach disk. If --store-reference-secrets is used, ArgoCD-tracked Secrets also reach disk. These are clearly labelled in the manifest and are never passed to oc create, but their presence increases the sensitivity of the backup directory.

Area 7 — Ordering, finalizers, CA Secrets, dependent Secrets

MEDIUM F-09 restore.py:163-165 (build_plan)  |  restore.py:71-78 (_stage_for)

Stage-based sort after topological sort can move a dependency after its dependent.

In build_plan (line 163), lib.order_entries(items) produces a topologically ordered list. Immediately after (line 165), ordered.sort(key=lambda i: i["stage"]) re-sorts by stage — a stable sort, so topological order is preserved within a stage but not across stages.

Consider: a Secret in stage 5 that a Certificate in stage 6 depends on. After the sort, the Secret (stage 5) precedes the Certificate (stage 6) — correct. But if a restorable object (stage 5) has a dependency on another restorable object that _stage_for assigns to stage 7 (e.g., a ManageWorkspace-owned ConfigMap), the dependency would come after the dependent in the final order. The problems array (lines 168-172) is supposed to catch this, but it only checks whether a step's dependency has a higher order number. That check runs after the stage-sort, so it would catch the violation — but only as a warning in the plan, not a blocking error in apply_plan.

In practice, the current restorable set is Secrets and ConfigMaps (stage 5) which depend on other Secrets and ConfigMaps (also stage 5), so this issue does not manifest on today's data. However, adding a new restorable custom resource type could trigger it silently.

Tests at line 495-510 confirm that plan["problems"] is empty for the default test data, which is correct but does not exercise a cross-stage dependency.

LOW F-10 dr_lib.py:285-291 (classify)  |  dr_lib.py:143-148 (sanitize)

Finalizers on restorable operator-owned Secrets are stripped, which is correct — but the record of what was stripped is only in MANIFEST.json, not a blocklist for the operator.

Operator-owned, state-bearing Secrets (e.g. main-manage-encryption-secret) have ownerReferences and finalizers stripped before writing to disk (sanitize lines 142-147). This is the right behaviour: stale UIDs would cause GC deletion, and finalizers would block deletion on the target. The stripped items are recorded in entry["stripped"].

The restore.py apply step applies the sanitised YAML directly. There is no post-apply check that the restored Secret has not been re-adopted by an operator before the operator reconciles the owning CR. If an operator reattaches a finalizer to the restored Secret before stage 7 reconciliation, and then regenerates the Secret (overwriting it), the old data is lost. This is an operator-behaviour question, not a code defect, and is correctly called out in the README acceptance criteria. Rating: Low (documented caveat, not a code error).

Area 8 — Partial failures and misleading success status

MEDIUM F-11 restore.py:279-280 (apply_plan)  |  tests/test_dr.py:598-607

skipped_exists is treated as a success in report["ok"] regardless of whether the on-target object matches the backup.

return {"ok": all(r["result"] in ("created", "dry-run-ok", "skipped_exists") for r in results)}

When oc create returns AlreadyExists for an object, the tool records skipped_exists and counts it as a success. The already-existing object on the target is never inspected or diffed against the backup copy. For a state-bearing Secret (e.g. main-manage-encryption-secret), "already exists" could mean it was previously restored with old data, regenerated by the operator, or left over from a prior broken restore. Silently counting this as success could leave the restore incomplete.

The test at line 598-607 confirms the behaviour is as coded. The README documents that --overwrite uses oc apply to replace. The issue is that the summary "apply: OK" message does not distinguish between "created clean" and "skipped because already present".

Recommended fix: A separate ok_with_skips field in the report (e.g. all results are created or dry-run-ok) or at minimum a clear warning when any skipped_exists result occurs on a required entry.

MEDIUM F-12 backup-suite-manage.sh:90-116, 229-232  |  dr_lib.py:437-441 (cmd_record_skip)

An encryption failure on a required resource increments both FAILED and could increment REQUIRED_MISSING, but the skip is not recorded, so the manifest validation check for "required resource not backed up" does not fire for that specific item.

When python3 "$LIB" store exits non-zero (due to encrypt failure or any Python exception), the shell at line 101 only increments FAILED; it does not call record-skip. The manifest validation at dr_lib.py:621-623:

for s in manifest["skipped"]:
    if s["required"] and s["status"] != "skipped_policy":
        errors.append(f"required resource {s['id']} not backed up: {s['reason']}")

can only fire for entries that reached .skips.jsonl. A required resource that failed the Python store step never reaches the skips file, so the manifest's validation.errors array is clean for that resource even though it is missing. The overall backup still exits 2 (FAILED > 0), but the JSON validation result says "ok": true — which is misleading if something downstream only checks the JSON.

The test at test_dr.py:389-396 covers a missing required resource (not-found), which does go through record-skip. There is no test for an encrypt-failure on a required resource.

Area 9 — Tests: failure coverage; no real cluster contact

Overall: PASS. The test suite uses a read-only fake oc (fakes.py:163-184) that refuses all non-get verbs (exit 97) and is wired via a per-test PATH override so no real oc binary is ever reachable. The StaticChecks test at line 675-684 scans all scripts for mutating oc verbs.

LOW F-13 tests/test_dr.py:219-273 (BackupEndToEndTests)  |  tests/fakes.py:116-188

The fake oc binary is written to a shared cls.tmp directory; fixture files are named by counting directory entries, which is non-deterministic if tests run in parallel.

The fixture helper at line 240 names files as fixture-%d.json where %d = len(os.listdir(self.tmp)). If two tests call fixture() simultaneously (e.g., with -j parallelism), they could get the same filename. unittest is single-threaded by default, so this is not a current problem. However, the _cache dict at line 246 is a class-level mutable that is not thread-safe. The risk is Low given standard single-threaded usage.

More important gap: there is no test that calls backup-suite-manage.sh with a DR_ENCRYPT_CMD that succeeds on some objects and fails on others (simulating a transient partial encrypt failure). This would exercise F-12 above and confirm whether the manifest accurately reflects the partial state.

Must-fix before live read-only discovery or backup?

Live read-only discovery (discover.py) has no findings that must block it — no write paths, no credentials exposed, no cluster mutations possible.

Live backup (backup-suite-manage.sh): two items should be addressed first:

  • F-02 (High) — add the empty-output guard to decrypt_bytes. Trivial one-line fix; prevents an opaque AttributeError crash during any future encrypted restore.
  • F-06 (High) — add a warning/error in cmd_init and preflight when source_server or source_context is empty. Prevents the source-context safety guard from silently degrading.

The remaining Medium items are process/documentation gaps or future-proofing concerns; they do not prevent a safe read-only backup run.

Recommended single safest next action:

Fix F-02 (add empty-output check to decrypt_bytes, dr_lib.py:372) and F-06 (emit a warning/error when source_server or source_context is empty in restore.py:preflight and backup-suite-manage.sh init), then re-run the 67 offline tests. Both are one-line changes. Only after these two fixes are reviewed and merged: run discover.py read-only against the cluster (no data written, no Secret values read) and review the resulting inventory for the outstanding ambiguous classifications listed in POC-RESULTS.md §4 before attempting any backup.
