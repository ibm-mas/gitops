ArgoCD Notifications
===============================================================================
Adds custom failure -> recovered -> success Slack notifications for MAS applications to the ArgoCD notifications configuration.

<!--docs-include-start-->
## Overview

This chart contributes the following keys to the `argocd-notifications-cm` ConfigMap of the ArgoCD instance that manages the MAS applications:

- `service.webhook.slack`: a generic webhook service pointing at a Slack Incoming Webhook (`$slack-webhook-url`, read from the `argocd-notifications-secret` Secret).
- `template.custom-status`, `template.custom-status-recovered`, `template.custom-status-success`: the Slack messages.
- `trigger.on-custom-status`, `trigger.on-custom-status-recovered`, `trigger.on-custom-status-success`: the triggers.

The sources live in `files/`: `service.webhook.slack.yaml` becomes the service key, and each `files/stages/<stage>.yaml` holds the `template` and the `trigger` of one stage, which are rendered as the `template.<stage>` and `trigger.on-<stage>` keys.

The MAS application Applications generated by `ibm-mas-instance-root` subscribe to these triggers (via the `notifications.argoproj.io/subscribe.<trigger>.slack` annotations) when `notifications.slack_channel_id` is set.

Three alerts are sent, in order: failure -> recovered -> success.

| Trigger | Fires when |
|---------|------------|
| `on-custom-status` | The application is `Degraded`, or its last sync is `Error`/`Failed`. Latched until `on-custom-status-success` has been sent. |
| `on-custom-status-recovered` | A failure was sent, the app is `Synced`, the last sync `Succeeded` and health is no longer `Degraded`. Latched until `on-custom-status-success` has been sent. |
| `on-custom-status-success` | A recovery was sent and the app is `Healthy` and `Synced`. |

The controller forgets a trigger's "already sent" marker as soon as its condition turns false. The markers live in the `notified.notifications.argoproj.io` application annotation, so each stage latches (stays true after it fires) until the next stage has been sent, and the next stage requires the previous marker to exist. This enforces the order and sends each alert once. After success the latches release and the next failure alerts again.

## Configuration

### Values

```yaml
# Namespace of the ArgoCD instance (set by the cluster root from argo.namespace)
argo_namespace: openshift-gitops

# Optional. AVP reference to the Slack Incoming Webhook URL. When set, the chart adds the
# "slack-webhook-url" key to argocd-notifications-secret (set by the cluster root from
# notifications.slack_webhook_url). When empty, no Secret is rendered.
slack_webhook_url: ""
```

### Webhook URL from a secret reference

Store the webhook URL in the secrets vault and pass only the reference. For example, in the cluster's `ibm-mas-cluster-base.yaml`:

```yaml
notifications:
  slack_channel_id: SLACK_CHANNEL_ID
  slack_webhook_url: "<path:arn:aws:secretsmanager:us-east-2:123456789012:secret:my-account/my-cluster/slack#slack_webhook_url>"
```

The Secret is applied with `ServerSideApply` and `Prune=false,Delete=false`, so only the `slack-webhook-url` key is owned by this chart. Other keys in `argocd-notifications-secret` (for example `slack-token`) are left untouched. Never put the plain URL in git.

### Prerequisites

- The notifications controller is enabled on the ArgoCD instance.
- The `argocd-notifications-secret` Secret of that instance contains the key `slack-webhook-url` with the Slack Incoming Webhook URL. Either set `slack_webhook_url` (see below) so this chart adds the key from a secret reference, or create the key by hand. The plain URL is never stored in git.
- The Application is created with `ServerSideApply=true`, and the ConfigMap is annotated `Prune=false,Delete=false`, so only the keys owned by this chart are managed and other notification configuration in the ConfigMap is left untouched.

The Application is only rendered by the cluster root when both `cluster_admin_role` and `notifications.slack_channel_id` are set.

